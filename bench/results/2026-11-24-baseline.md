- 关联 issue：[#3 建立 DataX 参考基线与新平台性能目标](https://github.com/maousan/go-datax/issues/3)
- 采集分支：`bench/perf-baseline`
- Harness 与复现步骤：[`bench/README.md`](https://github.com/maousan/go-datax/blob/bench/perf-baseline/bench/README.md)

- 引擎：`v1.4.0`，代码基线 `b8cfdf6`；本分支只新增 `bench/`，没有修改引擎代码或 DataX 行为。

## 结论摘要

- 唯一可完整跑通的 channel=4 数据库→数据库基线是 **MySQL → PostgreSQL**（1,000,000 行、12 列、channel=4）：中位 **21,347 rows/s**（43.4–47.1 s），峰值工作集中位 **180.3 MB**（177.8–182.8 MB），3 次测量全部成功，目标表行数均为 1,000,000。
- **TXT 文件 → SQLite**（500,000 行、channel=1）：中位 **8,595 rows/s**（56.7–61.8 s），峰值工作集中位 **71.1 MB**（70.6–71.7 MB）。
- 补充场景 **MySQL → SQLite**（1,000,000 行、channel=1）：中位 **8,612 rows/s**（116.0–122.2 s），峰值工作集中位 **72.1 MB**（71.4–72.5 MB）。
- 两个简单字符串 transformer（`dx_substr` + `dx_replace`）的引擎计时中位 **0.84 s / 1,000,000 行**（4 个 task 累计）；与无转换场景相比墙钟差 +1.04 s（+2.2%），在运行噪声范围内；进程 CPU 时间从 16.6–17.0 s 增至 19.6–20.6 s。
- **MySQL → MySQL（S1/S2）无法运行**：`mysqlwriter` 把 Java JDBC 专有参数 `yearIsDateType`、`zeroDateTimeBehavior` 写进 Go MySQL DSN，连接阶段报 `Error 1193 (HY000): Unknown system variable ...`。按 ticket 要求未改引擎；用同源、同数据量、同 Transformer 的 MySQL → PostgreSQL 场景替代测量，MySQL 作为目标端的数据仍缺失。
- 失败恢复（1,000,000 行 MySQL → PostgreSQL，第 10 秒强杀 + 清理 + 全量重跑）：恢复时间中位 **34.7 s**（33.6–50.6 s），重跑后 1,000,000 行全部校验通过。

### 阻塞项：S1/S2 无法运行

S1、S2 的配置保留在仓库中，但当前引擎无法执行。实测失败记录见
[`raw/s1-blocked-probe-iter0.json`](https://github.com/maousan/go-datax/blob/bench/perf-baseline/bench/results/raw/s1-blocked-probe-iter0.json)：

```
exit code 1（0.16 s）
job preparation failed: writer job prepare failed: failed to connect for pre SQL:
failed to connect to database: Error 1193 (HY000):
Unknown system variable 'zeroDateTimeBehavior'
```

另一次运行报的是 `Unknown system variable 'yearIsDateType'`，具体名字取决于 Go map 的遍历顺序。根因在
`plugins/writer/mysqlwriter/mysql_writer.go`：构造 DSN 时硬编码了 Java JDBC 专有的
`yearIsDateType=false`、`zeroDateTimeBehavior=convertToNull`，go-sql-driver 会把不认识的 DSN 参数当作
session 变量执行 `SET`，MySQL 服务端没有这两个变量，连接失败。`mysqlreader` 本身可用，但配置里
带 `?useUnicode=true&characterEncoding=utf8` 也会触发同类错误；基线配置使用不带参数的
`jdbc:mysql://127.0.0.1:13306/datax_bench`。

Ticket 明确要求“不改引擎行为”，因此没有修复该缺陷，也没有用代理/补丁绕过。后果：

- 没有 MySQL 作为目标端的参考基线；
- S2 的 Transformer 开销改在同源、同数据量、同 channel 的 MySQL → PostgreSQL 路径上测量（S2' 对 S4）；
- 新平台如果首发支持 MySQL Sink，DataX 侧没有可直接对比的 MySQL Sink 数字，目标值是暂定。

S3 只用 1 个 channel：`txtfilereader` 按文件分片，单个文件无法分给 4 个 channel。
S5 只用 1 个 channel：SQLite 是单写者，4 个 writer task 并发写同一个库会串行化或 `SQLITE_BUSY`。

## 测量方法

每个场景：1 次 warm-up（记录但不计入中位数/范围）+ 3 次正式测量。

- 引擎直接以子进程启动：`bin/datax.exe -job <config>`，不经过 shell。
- **墙钟耗时**：`Stopwatch` 包围进程从启动到退出，包含进程启动、配置解析、连接、传输和关闭。
- **rows/s（墙钟）**：引擎报告的读取行数 ÷ 进程生命周期，是报告的主指标。
- **rows/s（引擎）**：引擎最终日志的 `Record Write Speed`，只除以它自己的传输窗口，用于交叉检查。
- **峰值内存**：25 ms 轮询 `System.Diagnostics.Process`，每次读取 OS 维护的 `PeakWorkingSet64`
  高水位；进程退出后该计数器不可读，因此最后若干次轮询可能错过退出前的瞬时峰值。
  同时记录采样的 `PrivateMemorySize64` 最大值。只测 `datax.exe` 进程，不含数据库容器。
- **退出码**：进程退出码；所有正式测量均为 0。
- **目的地校验**：每轮结束后独立统计目标表行数（MySQL/PostgreSQL 用容器内 SQL，SQLite 用只读
  `verify-sqlite.py`），12 次正式测量全部等于期望值（1,000,000 或 500,000）。
- **重置**：MySQL/PostgreSQL 目的表在每轮前 `TRUNCATE`；SQLite 文件在每轮前删除，由 job 的
  `preSql` 重建。作业内部还会执行 `preSql: TRUNCATE TABLE bench_dest`，这部分计入测量窗口。
- **原始记录**：每轮 `bench/results/raw/<label>-iter<N>.json` 记录配置、命令、引擎 SHA256、耗时、
  rows/s、峰值内存、CPU 时间、引擎字节、Transformer 计数和退出码；stdout/stderr 日志同目录。
  汇总在 `bench/results/raw/summary.csv`。

S4 的实测 `engineRecordSpeed` 为 23,255 / 23,255 / 21,739 rec/s，而墙钟 rows/s 为
21,239 / 23,016 / 21,347；差异来自进程启动、连接与关闭。报告以墙钟为准。

### 失败恢复

方法：MySQL → PostgreSQL（S4 配置，1,000,000 行），传输开始约 10 s 时强制结束 `datax.exe`
（模拟崩溃，不做清理）；记录已提交行数，执行 `TRUNCATE` 清理，再启动同一 job 直到成功。
恢复时间 = 从强杀到重跑成功退出的墙钟时间；DataX 没有 checkpoint，恢复就是全量重跑。

| 轮次 | 强杀时刻 s | 已提交行数 | 重跑耗时 s | 恢复时间 s | 重跑峰值 WS MB | 重跑行数 | 校验 |
|---|---:|---:|---:|---:|---:|---:|---|
| 1 | 10.333 | 346,112 | 33.389 | 34.721 | 180.4 | 1,000,000 | 通过 |
| 2 | 10.236 | 269,312 | 32.681 | 33.578 | 180.0 | 1,000,000 | 通过 |
| 3 | 10.237 | 332,800 | 49.778 | 50.625 | 180.1 | 1,000,000 | 通过 |
| 中位 | 10.237 | 332,800 | 33.389 | **34.721** | 180.1 | 1,000,000 | — |

已提交行数不为 0，是因为 writer 每 1024 行批量提交；崩溃后这些批次不会回滚，重试前需要清理
目标表（本次用 `TRUNCATE`）。恢复时间的中位 34.7 s 小于正常运行的 46.8 s，因为重跑时 PostgreSQL
和文件缓存更热，且没有其他场景并行；范围 33.6–50.6 s 反映了这种波动。

## 局限与注意事项

1. **MySQL → MySQL 缺失**：`mysqlwriter` 与真实 MySQL 8.0.46 不兼容（Java JDBC 参数被当作 session
   变量），S1/S2 无法测量；MySQL 作为 Sink 的性能没有 DataX 参考数字。S4/S2' 是替代测量，不能等价
   视为 MySQL Sink 基线。
2. **存储是主要噪声源**：Docker Desktop/WSL2 卷所在磁盘接近满（运行期间剩余 16–18 GB），
   MySQL 1M 行 `LOAD DATA` 约 6 分钟；PostgreSQL `synchronous_commit=on` + 1024 行批量提交，
   墙钟范围可达 ±10–20%。3 次测量的中位数只代表本机本次状态，不是稳定容量规划数字。
3. **只有一台机器、3 次测量**：没有 CPU 绑核、频率锁定、置信区间；后台还有 Docker、管理台
   `datax-server`（约 27 MB）和系统进程。不同机器/容器资源下的绝对值会不同。
4. **内存口径**：峰值 WS 只统计 `datax.exe` 进程；PostgreSQL/MySQL 容器各限 4 GiB，不计入。
   `PeakWorkingSet64` 是 OS 高水位，但轮询在进程退出前最后一次读取之后发生的瞬时峰值可能漏掉。
5. **S3/S5 是单 channel**：文件按文件分片、SQLite 单写者，不能与 channel=4 的 DB→DB 场景直接比较
   rows/s；它们衡量的是单线程路径。
6. **字节口径**：引擎字节是 element 计费，不是 CSV、磁盘或网络字节；CSV 1M 行是 172.8 MB，
   引擎报告 146.5 MiB。
7. **日志成本**：MySQL/TXT reader 每 1000 行打一条进度日志，属于 DataX 当前行为，计入基线；
   新平台若降低日志量，吞吐会更高，比较时需说明。
8. **恢复只测了 MySQL → PostgreSQL**：没有测 SQLite/文件场景的恢复；DataX 没有断点续传，
   恢复时间等于清理 + 全量重跑，不包含调度器重试退避。

## 新平台目标工作负载与候选指标

> **提案，待用户确认，不是承诺。** 以下数字由本次 DataX 基线推导，用于启动讨论；确认前不应作为
> 验收标准或对外承诺。新平台是独立实现，不需要以 DataX 的插件/子进程模型为约束。

### 参考线规则

DataX 基线只作“不要比它慢”的参考线：同一场景、同一硬件、同一数据量下，新平台的墙钟 rows/s
不应低于本报告对应数字，峰值 RSS 不应高于基线 + 64 MiB。由于 MySQL Sink 基线缺失，MySQL Sink
的参考线在补测前暂不生效。

### 候选工作负载

| Profile | 工作负载 | 候选绝对目标 | 依据/说明 |
|---|---|---|---|
| A. 小批量高频 | 10,000–100,000 行 × 12 列，DB 或文件源，1–5 分钟一次；单机 | 100k 行端到端 ≤ 2.0 s（≥ 50,000 rows/s，不含调度排队）；10k 行 ≤ 0.5 s；进程启动 ≤ 300 ms；峰值 RSS ≤ 128 MiB；失败到重跑成功 ≤ 15 s | 小批量可全部命中缓存，目标高于 1M 基线；内存上限按 100k 行有界批次设定 |
| B. 大批量装载 | 1,000,000 行 × 12 列，DB→DB，channel=4；可扩展到 10M 行 | 1M 行端到端 ≤ 25 s（≥ 40,000 rows/s）；10M 行持续 ≥ 40,000 rows/s；峰值 RSS ≤ 256 MiB @1M、≤ 384 MiB @10M，且不随行数线性增长；1M 行失败恢复 ≤ 60 s（10M ≤ 10 min） | 基线 21,347 rows/s / 180 MB；目标约为 1.9× 吞吐，内存只增加约 40%，需要批量/COPY 式写入而不是逐行 INSERT |
| C. Transform-heavy | 1,000,000 行 × 12 列，5 个 Transform（substr/replace/regex/filter/digest 组合），DB→DB | 端到端 ≥ 25,000 rows/s；Transform CPU ≤ 总进程 CPU 的 25%；相对同 Sink 无转换场景墙钟回退 ≤ 10%；峰值 RSS ≤ 320 MiB；1M 行失败恢复 ≤ 90 s | 基线 2 个 Transform 为 20,883 rows/s；CPU 从 17 s 增至 20 s，说明转换链是主要可控成本；5 个 Transform 仍要求高于基线 |

### 指标定义（提案）

- **rows/s**：与本文一致，引擎成功写入/读取的行数 ÷ 端到端墙钟；报告同时给出引擎传输窗口口径。
- **内存上限**：新平台运行时进程的 OS `PeakWorkingSet64`；不含数据库/外部服务。
- **恢复时间**：从故障检测到同一工作负载重跑成功退出；当前提案按“清理 + 全量重跑”计，
  不包含调度器重试退避。若后续引入 checkpoint/续跑，需另立指标。
- **硬件**：暂以本机（i5-9600KF / 48 GB / NVMe）为基准；如果目标部署硬件不同，应按比例重测，
  不能直接搬运绝对数字。

### 待用户确认

1. 三个 Profile 是否覆盖首批目标工作负载？是否还需要宽表（>50 列）、大字段（JSON/BLOB）、
   多表/分片、跨库同步等 Profile？
2. 内存上限用 RSS 还是 Go heap？本提案用 RSS，便于和 DataX 基线对比。
3. 恢复时间是否包含调度器 retry/backoff？是否要求 checkpoint 续跑，还是首批只做全量重试？
4. MySQL Sink 是否在首批范围？如果在，需要先补一个可工作的 MySQL Sink 基线（修复 DataX
   `mysqlwriter` 或在新平台连接器上单独测量），否则 MySQL Sink 目标只能暂定。
5. 目标硬件的基线是否就是本机？若不是，需要在新硬件上重跑本 harness 后再定绝对值。
